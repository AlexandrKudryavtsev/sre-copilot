# Как запустить SRE Copilot и вручную создать тестовый инцидент

Основной сценарий занимает примерно 5–10 минут после сборки контейнеров.
Понадобятся Docker Desktop, браузер и терминал. Java, Maven и Node.js на компьютере
для этого способа запуска не нужны.

## Что именно создаёт инцидент

В проекте есть `demo-service` — тестовый сервис, который сам генерирует
Prometheus-метрики. Его можно переключать между «нормальной работой» и «перегрузкой».

Мы создадим правило: **если CPU ≥ 80% на трёх проверках подряд, открыть инцидент**.
Затем переключим demo-service в перегрузку, где CPU около 95%.
Backend увидит нарушение правила, создаст инцидент и автоматически запустит AI-анализ.

Команда переключения сценария меняет тестовые метрики. Сам Incident создаёт Rule Engine
после проверок. Генератор не перегружает настоящий CPU компьютера, а имитирует нагрузку.
Отдельно слать тысячи запросов или запускать нагрузочный тест не нужно.

## 1. Подготовь запуск

Запусти Docker Desktop и дождись, пока он будет готов. Открой терминал и перейди
в каталог проекта:

```sh
cd /Users/alexander/Development/sre-copilot
```

Все дальнейшие команды выполняй из этого каталога.

Открой корневой файл `.env`. Он уже должен существовать и содержать твой `OPENAI_TOKEN`.
Если файла нет, создай его командой:

```sh
test -f .env || cp .env.example .env
```

Добавь или измени следующие строки в `.env`, сохранив остальные настройки:

```dotenv
OPENAI_TOKEN=твой_настоящий_токен
OPENAI_MODEL=gpt-4o-mini
OPENAI_BASE_URL=https://api.openai.com/v1
AI_SCHEDULER_ENABLED=true
AI_REQUEST_TIMEOUT=30s
AI_POLL_INTERVAL=1s
MONITORING_SCHEDULER_ENABLED=true
MONITORING_COLLECTION_INTERVAL=5s
MONITORING_RECOVERY_CHECKS=3
DEMO_SCENARIO=normal
```

`OPENAI_TOKEN=твой_настоящий_токен` — образец: оставь свой действующий токен,
не вставляй эту надпись буквально. Не создавай несколько строк с одной переменной.

Интервал сбора `5s` нужен, чтобы не ждать по полторы минуты на каждый переход.
Это также текущее значение по умолчанию. В существующем `.env` может оставаться `30s`,
поэтому проверь настройку перед запуском.

## 2. Запусти весь стек

```sh
docker compose up --build -d --wait
```

Команда собирает и запускает frontend, backend, PostgreSQL и demo-service.
Первая сборка может занять несколько минут.

Проверь состояние контейнеров:

```sh
docker compose ps
```

Ожидаемый результат: четыре сервиса запущены и имеют состояние `healthy`.

Адреса при стандартных портах:

| Что открыть | Адрес |
|---|---|
| Интерфейс SRE Copilot | http://localhost:5173 |
| Проверка backend | http://localhost:8080/actuator/health |
| Состояние demo-service | http://localhost:8081/scenario |
| Исходные тестовые метрики | http://localhost:8081/metrics |
| Swagger | http://localhost:8080/swagger-ui.html |

Backend health должен показать `"status":"UP"`.
Если ты менял порты в `.env`, используй свои значения вместо `5173`, `8080`, `8081`.

Верни генератор в нормальный режим, даже если он уже был запущен раньше:

```sh
curl -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"normal"}'
```

В ответе должно быть `"scenario":"normal"`.

## 3. Создай тестовый проект в браузере

Открой http://localhost:5173 и перейди в **Projects → New project**.
Заполни форму:

| Поле | Значение |
|---|---|
| Project name | `Demo AI check` |
| Description | Можно оставить пустым |
| Endpoint type | `PROMETHEUS` |
| Endpoint URL | `http://demo-service:8081/metrics` |

Нажми **Create project**, затем открой созданный проект.

Здесь нужен именно адрес `demo-service`, потому что запрос к метрикам выполняет backend
в Docker. `localhost:8081` внутри backend-контейнера адресует сам контейнер,
а не demo-service. При этом команды `curl` из терминала компьютера используют
`http://localhost:8081`, как в примерах выше.

На Overview:

1. Нажми **Test connection**. Проверка должна пройти, статус — `CONNECTED`.
2. Нажми **Enable monitoring**. Кнопка сменится на **Pause monitoring**.
3. Подожди 30–60 секунд. Можно нажать **Refresh** на Overview.
4. Убедись, что появились значения Golden Signals и точки на графиках.

В режиме `normal` ожидаются приблизительно:

- Latency — 80 мс.
- Traffic — 20 req/s.
- Errors — около 0.5%, с заметными случайными колебаниями на коротких интервалах.
- Saturation — 20%.

Для первых метрик нужны два опроса: первый задаёт базовую точку счётчиков,
второй позволяет посчитать показатели. При сборе раз в 5 секунд обычно хватает
около 10 секунд, а Overview проверяет текущие метрики каждые 5 секунд.
Дополнительное ожидание даёт AI несколько точек нормальной работы для сравнения.

## 4. Создай правило для инцидента

На Overview нажми **Manage rules**, затем **New rule**.

| Поле | Значение |
|---|---|
| Rule name | `High CPU demo` |
| Golden Signal | `Saturation (%)` |
| Comparison | `≥ Greater than or equal` |
| Threshold | `80` |
| Incident severity | `Critical` |
| Check interval (seconds) | `5` |
| Consecutive violations | `3` |
| Enable rule | Галочка включена |

Нажми **Create rule**.

Смысл настройки: раз в 5 секунд проверять новый snapshot и открыть инцидент
после трёх подряд значений CPU ≥ 80%. Число `3` означает количество проверок,
а не секунды. Одного высокого значения недостаточно.

В нормальном режиме правило должно быть включено, а его runtime state — `HEALTHY`.

## 5. Включи перегрузку и дождись инцидента

В терминале выполни:

```sh
curl -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"overloaded"}'
```

В ответе должно быть `"scenario":"overloaded"`.

Теперь генератор отдаёт примерно 95% CPU, 150 req/s, 650 мс latency и 8% ошибок.
Значения немного меняются случайным образом. Saturation стабильно превышает наш порог 80%.

Оставь этот сценарий включённым хотя бы на 30 секунд. В браузере открой **Rules**
или **Incidents** у тестового проекта. При необходимости нажми **Refresh**
или обнови страницу.

Ожидаемые переходы:

```text
HEALTHY → VIOLATING → INCIDENT_OPEN
```

После трёх нарушений появится один инцидент **Open / Critical**, связанный с правилом
`High CPU demo`. Обычно это занимает около 15–25 секунд плюс ожидание обновления
интерфейса. Если одновременно мониторится много проектов, время может быть больше.

Открой инцидент из списка **Incidents** или по ссылке в карточке правила.
Номер может быть любым: `INC-1`, `INC-7`, `INC-42` — используй реально появившийся инцидент.

## 6. Проверь AI Analysis

В деталях инцидента должен появиться блок **AI Analysis**.

Сначала он показывает **Analyzing / Analyzing incident…**, затем обычно **Completed**.
Frontend сам проверяет результат каждые 3 секунды. Быстрый ответ может завершиться
до того, как ты откроешь страницу, — тогда сразу увидишь Completed.

При Completed проверь, что отображаются:

- **Probable cause** — гипотеза о причине проблемы.
- **Evidence** — данные, на которых основан вывод.
- **Recommended actions** — нумерованные действия для проверки и устранения.
- Время анализа и предупреждение о необходимости проверки AI-выводов.

Названия интерфейса на английском, текст модели обычно на русском.
Для проверки не нужно ждать накопления полных 30 минут истории: модель получает
имеющиеся реальные snapshots из этого окна.

Также возможны состояния:

| Что видишь | Значение и действие |
|---|---|
| Failed | Запрос к OpenAI не удался. Прочитай сообщение, исправь причину и нажми **Retry Analysis**. |
| Insufficient data | Модель не смогла обосновать полезную гипотезу. Посмотри объяснение и рекомендации. Это допустимый ответ. |
| No analysis yet | Инцидент создан до добавления AI. Нажми **Analyze incident**, либо создай новый инцидент по этой инструкции. |
| Сообщение о недоступности backend | Не удалось прочитать состояние анализа. Нажми **Try again** после восстановления соединения. |

Чтобы проверить повторный запуск, нажми **Retry Analysis** на завершённом анализе.
Ожидается новый переход **Analyzing → Completed** или другое конечное состояние.
Во время запуска кнопка блокируется; после принятия запроса прежний результат очищается.
Retry выполняет настоящий запрос к OpenAI, но не создаёт новый Incident.

AI-выводы — гипотезы. В частности, упоминание СУБД, памяти или дисков не является
подтверждённым фактом, если в переданных метриках таких данных нет.

## 7. Верни сервис в норму и проверь закрытие

```sh
curl -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"normal"}'
```

Оставь мониторинг и правило включёнными. После трёх здоровых проверок CPU < 80%
backend автоматически закроет инцидент.

Подожди примерно 15–30 секунд, затем проверь детали или список инцидентов.
Статус должен стать **Resolved**, появится время восстановления, длительность перестанет расти.
AI-результат сохранится. Ошибка AI не мешает закрытию инцидента.

**Pause monitoring** и **Disable rule** приостанавливают проверки, включая закрытие.
Они сами по себе не переводят инцидент в Resolved.

## 8. Как получить ещё один инцидент

После того как первый стал **Resolved**, снова выполни команду `overloaded` из шага 5.
Три новых нарушения создадут новый инцидент с новым номером и отдельным AI-анализом.
Затем снова верни `normal`.

Пока прежний инцидент остаётся Open, длительная перегрузка не создаёт копии:
для одного правила может быть только один открытый инцидент.

## Другие сценарии для экспериментов

CPU-проверка выше — самый простой и устойчивый вариант. Можно создать другое правило
и переключить соответствующий сценарий той же командой `POST /scenario`.

| Сценарий | Пример подходящего правила | Что получится |
|---|---|---|
| `slow` | Latency ≥ 800 мс, 3 нарушения | Инцидент высокой задержки; задержка около 900 мс. |
| `errors` | Errors ≥ 10%, 3 нарушения | Инцидент ошибок; ошибок около 25%. |
| `overloaded` | Saturation ≥ 80%, 3 нарушения | Инцидент CPU; CPU около 95%. |
| `normal` | Низкие значения сигналов | Восстановление для перечисленных правил. |
| `unavailable` | Endpoint метрик отдаёт HTTP 503 | Проект станет UNAVAILABLE, новые snapshots не появятся. Сам по себе этот сценарий не создаёт инцидент недоступности. |

Для другого сценария замени `overloaded` в JSON команды на `slow` или `errors`.
При коротких интервалах значения latency/errors случайно колеблются, поэтому время
открытия может отличаться. Возвращай `normal` между отдельными экспериментами.

## Если что-то не получилось

| Проблема | Что проверить |
|---|---|
| Страница не открывается | `docker compose ps`; frontend должен быть healthy. Проверь порт `FRONTEND_PORT` в `.env`. |
| Изменения интерфейса не появились | Пересобери frontend: `docker compose up --build -d --wait frontend`, затем обнови страницу. |
| Test connection не проходит | У проекта должен быть URL `http://demo-service:8081/metrics`; demo-service должен работать в сценарии `normal`. |
| Метрик нет | Проект должен мониториться, `MONITORING_SCHEDULER_ENABLED=true`; дождись двух опросов и обновления UI. |
| Инцидент не создаётся | Включены мониторинг и правило; сценарий `overloaded`; Saturation ≥ 80; три нарушения; интервалы сбора и правила действительно по 5 секунд. |
| Инцидент не закрывается | Верни `normal`, оставь мониторинг и правило включёнными, дождись трёх здоровых проверок. |
| `OPENAI_TOKEN is not configured.` | Проверь токен в корневом `.env` и пересоздай backend командой ниже, затем Retry Analysis. |
| `OpenAI returned HTTP 401.` | Проверь действующий `OPENAI_TOKEN`; после изменения пересоздай backend и повтори анализ. |
| `OpenAI returned HTTP 429.` | Проверь доступность запросов и ограничения API в своём аккаунте; повтори анализ позже. |
| Timeout или ошибка соединения с OpenAI | Проверь доступ к OpenAI из backend. При необходимости увеличь `AI_REQUEST_TIMEOUT` и пересоздай backend. |
| Анализ долго остаётся Analyzing | Проверь `AI_SCHEDULER_ENABLED=true` и логи backend. После перезапуска незавершённая попытка может ждать истечения lease: timeout запроса + 60 секунд. |
| По-прежнему ждёшь около 90 секунд | Вероятно, сбор или правило настроены на 30 секунд. Изменение только интервала правила не ускоряет сбор snapshots. |

После изменения `.env` примени новые переменные:

```sh
docker compose up -d --wait backend
```

Обычный `docker compose restart backend` не подхватывает новые переменные окружения
из `.env`: для этого нужно пересоздание контейнера через `up`.
Если менял исходный код backend, используй `docker compose up --build -d --wait backend`.

Посмотреть логи:

```sh
docker compose logs --tail=100 backend
```

Наблюдать логи в реальном времени:

```sh
docker compose logs -f backend
```

`Ctrl+C` завершит просмотр логов, сами контейнеры продолжат работать.

## Завершение проверки

Перед завершением верни `normal`, чтобы генератор не оставался в перегрузке.
Стек можно оставить запущенным либо остановить:

```sh
docker compose down
```

Обычный `down` сохраняет БД: проекты, правила, инциденты и AI-результаты останутся
при следующем запуске. **Не добавляй `-v`, если хочешь сохранить эти данные.**

### Что должно получиться

- [ ] Стек запустился, frontend открывается.
- [ ] Проект подключён к demo-service, Golden Signals появляются.
- [ ] Правило включено, в `normal` инцидента нет.
- [ ] После `overloaded` создан Open / Critical incident.
- [ ] AI Analysis показал конечный статус и результат либо понятную ошибку.
- [ ] Retry Analysis повторно запустил анализ.
- [ ] После `normal` инцидент автоматически стал Resolved.
- [ ] Повторный `overloaded` после восстановления создал новый инцидент.
