# SRE Copilot

Система мониторинга сервисов: собирает метрики, показывает четыре Golden Signals,
открывает и закрывает инциденты по правилам и помогает разобрать их причины с помощью AI.

## Запуск и остановка

Нужен Docker с Docker Compose. Все команды выполняются из корня репозитория;
Java, Node.js и Python на компьютере устанавливать не нужно.

```sh
test -f .env || cp .env.example .env
docker compose up --build -d --wait
```

| Что открыть | Адрес |
|---|---|
| Интерфейс | <http://localhost:5173> |
| Swagger: описание и вызов API | <http://localhost:8080/swagger-ui.html> |
| Метрики demo-service | <http://localhost:8081/metrics> |

Compose запускает frontend, backend, PostgreSQL и demo-service. Порты и настройки
можно изменить в `.env`; команды ниже рассчитаны на порты по умолчанию.

Для AI-анализа укажите `OPENAI_TOKEN` в `.env` перед запуском. Если контейнеры уже
работают, примените настройку командой `docker compose up -d --wait backend`.
Без ключа мониторинг и инциденты работают, но AI-анализ завершится ошибкой.
После настройки ключа его можно повторить кнопкой `Retry` на странице инцидента.

Проверить состояние и посмотреть логи:

```sh
docker compose ps
docker compose logs -f backend
```

Остановить систему, сохранив проекты, правила и историю в базе:

```sh
docker compose down
```

Для следующего запуска используйте ту же команду `docker compose up --build -d --wait`.
Если нужно удалить также базу и начать с чистого состояния:

```sh
docker compose down -v
```

## Проверка через demo-service

Demo-service генерирует синтетические метрики без дополнительной нагрузки с вашей
стороны. Сценарии меняют значения метрик, а не реальную загрузку компьютера.

### Подключить проект и правила

1. Откройте интерфейс и создайте проект `Demo service`.
2. Выберите тип endpoint `Prometheus` и URL `http://demo-service:8081/metrics`.
   Backend обращается к сервису внутри Docker-сети, поэтому здесь нужно имя
   `demo-service`, а не `localhost`.
3. На странице проекта проверьте подключение и включите мониторинг.
4. В разделе `Rules` создайте включённые правила из таблицы ниже. Для каждого
   задайте интервал проверки **5 секунд** и **3 последовательных нарушения**.

| Название правила | Golden Signal | Условие | Severity |
|---|---|---|---|
| High CPU | Saturation | ≥ 80% | Critical |
| High latency | Latency | ≥ 500 мс | Warning |
| High errors | Errors | ≥ 10% | Critical |

Первые метрики появятся после двух опросов, обычно через 10–15 секунд.
В `Overview` видны показатели и графики, в `Rules` — прогресс проверок,
в `Incidents` — открытые и завершённые инциденты.

### Открыть и закрыть инцидент

Включите перегрузку:

```sh
curl --fail-with-body -sS -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"overloaded"}'
```

CPU поднимется примерно до 95%, задержка — до 650 мс. При указанных выше правилах
примерно через 15–30 секунд откроются инциденты `High CPU` и `High latency`.
Откройте их в `Incidents`: там доступны условие срабатывания, метрики и AI-анализ.

Верните нормальный режим:

```sh
curl --fail-with-body -sS -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"normal"}'
```

CPU вернётся примерно к 20%, задержка — к 80 мс. После трёх последовательных
проверок без нарушения инциденты автоматически перейдут в `RESOLVED`.
Обычно это занимает 15–30 секунд; интерфейс может показать новый статус чуть позже.
**Кнопки ручного закрытия нет.** Для восстановления оставьте мониторинг и правила включёнными.

### Другие сценарии

Запускайте сценарии по одному. Между проверками возвращайте `normal` командой выше
и дожидайтесь закрытия предыдущих инцидентов.

Высокая задержка: около 900 мс, сработает `High latency`.

```sh
curl --fail-with-body -sS -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"slow"}'
```

Ошибки: около 25% ответов 5xx, сработает `High errors`.

```sh
curl --fail-with-body -sS -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"errors"}'
```

Недоступность источника метрик:

```sh
curl --fail-with-body -sS -X POST http://localhost:8081/scenario \
  -H 'Content-Type: application/json' \
  -d '{"name":"unavailable"}'
curl -i http://localhost:8081/metrics
```

Последняя команда вернёт `503 Service Unavailable`. Backend отметит подключение
как недоступное, новые точки метрик перестанут поступать. Отдельный инцидент
по недоступности не создаётся: правила проверяют числовые метрики.
Существующие инциденты тоже не закрываются до восстановления сбора.
Для восстановления снова включите `normal`.

Посмотреть текущий сценарий и исходные метрики:

```sh
curl --fail-with-body -sS http://localhost:8081/scenario
curl -i http://localhost:8081/metrics
```

## Как работает система

Backend опрашивает endpoint каждого проекта с включённым мониторингом, по умолчанию
с паузой **5 секунд** между циклами. Из Prometheus-метрик рассчитывает показатели,
сохраняет историю в PostgreSQL и проверяет правила. Frontend периодически запрашивает
результаты у backend; текущие метрики на открытой странице обновляются каждые 5 секунд.

Правило задаёт показатель, порог, интервал проверки, число последовательных нарушений
и серьёзность. После нужного числа нарушений открывается один инцидент на правило.
Три успешные проверки подряд закрывают его; это число настраивается через
`MONITORING_RECOVERY_CHECKS`. Инцидент сохраняет условие, по которому он открылся:
редактирование правила не меняет условие закрытия уже открытого инцидента.

При открытии инцидента AI получает его контекст и историю метрик перед срабатыванием,
чтобы предложить возможную причину и действия для проверки. Анализ помогает расследованию;
он не меняет правила и не исправляет сервис автоматически.

### Что нужно знать из SRE

**SRE** — подход к обеспечению надёжности сервисов. Здесь используются четыре
**Golden Signals**, которые помогают заметить ухудшение работы:

| Показатель | Что означает в этой системе |
|---|---|
| Latency | Среднее время запроса в миллисекундах; это не p95 или p99 |
| Traffic | Число запросов в секунду |
| Errors | Доля ответов HTTP 5xx; ответы 4xx не считаются ошибками |
| Saturation | Загрузка CPU в процентах; другие ресурсы здесь не учитываются |

**Инцидент** — устойчивое нарушение условия правила. Последовательные проверки
отсекают одиночные скачки, а `Warning` / `Critical` задают серьёзность проблемы.
Пороги выбирают под конкретный сервис: значения в примере нужны для демонстрации.

Отсутствие трафика или метрик не доказывает, что сервис здоров. При нулевом трафике
проверки Latency и Errors не засчитываются ни как нарушение, ни как восстановление.
При недоступном endpoint проверка правил ждёт новых метрик. Отключение правила
или мониторинга также останавливает проверки и не закрывает инциденты.
